# 2팀 리팩토링 가이드

프로젝트 종료 후 포트폴리오 완성도와 실무 운영 안정성을 높이기 위해 아래 4가지 핵심 과제를 순서대로 리팩토링하는 것을 권장합니다.

## 1. AI 어시스턴트 모델 자동 폴백(Failover / Fallback) 체인 구현
- 현황 및 문제점: AI 모델 서비스(AiModelService)에서 프론트엔드가 전달한 단일 모델명을 기준으로 스위치 분기하여 호출하고 있어, 업무 사용자가 개별 모델의 성능·한도를 직접 파악해야 하고 특정 모델의 무료 쿼터 소진(429)이나 일시적 응답 지연 발생 시 질의가 즉시 실패합니다. 또한 MCP 툴 콜백 배열 전달 시 가변인자 컴파일 경고가 발생하고 있습니다.
- 리팩토링 방향: 사용자 모델 선택 파라미터 의존을 제거하고, 서버 내부에 성능 우선순위 모델 체인(상위 Gemini 모델 -> 경량 Gemini 모델 -> Groq 대체 모델)을 정의하여 순차 호출하되 예외 발생 시 자동으로 다음 순위 모델로 전환(Fallback)하도록 개선합니다.

```java
private static final List<String> MODEL_FALLBACK_ORDER = List.of(
        "gemini-2.5-flash",
        "gemini-2.5-flash-lite",
        "openai/gpt-oss-120b",
        "openai/gpt-oss-20b"
);

public AiDto.AskExecution askWithDetails(
        AiDto.AskRequest request,
        String accessToken,
        List<AiDto.HistoryMessage> history
) {
    Exception lastException = null;

    for (String candidateModel : MODEL_FALLBACK_ORDER) {
        try {
            ChatClient selectedClient = resolveClient(candidateModel);
            log.info("AI 질의 시도 모델: {}", candidateModel);
            return askWithMcp(selectedClient, request.message(), accessToken, candidateModel, history);
        } catch (Exception e) {
            lastException = e;
            log.warn("AI 모델 호출 실패로 하위 모델 폴백 전환. 실패 모델={}, 사유={}", candidateModel, e.getMessage());
        }
    }

    throw new IllegalStateException("모든 AI 모델 호출에 실패했습니다.", lastException);
}
```

## 2. 공통 감사 엔티티(BaseTimeEntity) 캡슐화 및 출하 엔티티 연관관계 정비
- 현황 및 문제점: 거래처 엑셀 일괄 등록 시 기존 생성일·작성자 보존을 위해 BaseTimeEntity에 @PrePersist와 @PreUpdate를 적용한 설계는 타당하나, 클래스 상단에 public @Setter가 열려 있어 모든 하위 엔티티의 감사 필드가 외부 임의 변경에 노출되어 있습니다. 또한 출하(Shipment) 엔티티는 BaseTimeEntity를 상속받지 않고 수주 식별자를 단순 정수형(Long orderId)으로 보유하고 있습니다.
- 리팩토링 방향:
  1. BaseTimeEntity 클래스 상단의 @Setter를 제거하고, 엑셀 초기 데이터 적재 등 특수한 경우에만 하위 엔티티 내부에서 호출할 수 있는 protected 초기화 메서드를 제공합니다.
  2. Shipment 엔티티가 BaseTimeEntity를 상속받도록 변경하고, CustomerOrder와의 지연 로딩(@ManyToOne(fetch = FetchType.LAZY)) 연관관계를 매핑하여 엔티티 설계 일관성을 확보합니다.

```java
@Getter
@MappedSuperclass
public abstract class BaseTimeEntity {

    @Column(updatable = false, nullable = false)
    private LocalDateTime createdAt;

    @Column(nullable = false)
    private LocalDateTime updatedAt;

    @Column(updatable = false)
    private String createdBy;

    @Column
    private String updatedBy;

    protected void initAuditFieldsIfAbsent(LocalDateTime createdAt, String createdBy) {
        this.createdAt = createdAt;
        this.createdBy = createdBy;
    }
}
```

## 3. 컨트롤러 요청 검증(@Valid) 누락 보완 및 읽기 전용 트랜잭션 통일
- 현황 및 문제점: 거래처 엑셀 등록(ClientController), 품목 등록·수정·상태 변경(ProductController), 출하 운송장 등록(ShipmentController) 등 일부 컨트롤러 메서드의 @RequestBody 파라미터에 @Valid 어노테이션이 누락되어 DTO 내부의 Bean Validation 제약이 작동하지 않습니다. 또한 일부 서비스(CustomerOrderProgressService, ShipmentTrackingService, ProductionPlanRescheduleService) 클래스 레벨에 기본 쓰기 @Transactional이 선언되어 있습니다.
- 리팩토링 방향:
  1. 요청 본문을 수신하는 모든 컨트롤러 파라미터 앞에 @Valid를 누락 없이 선언합니다.
  2. 모든 서비스 클래스 상단에는 @Transactional(readOnly = true)를 기본 적용하고, 실제 데이터 변경이 일어나는 메서드에만 @Transactional을 개별 선언합니다.

## 4. 만료 리프레시 토큰 정리 스케줄러 추가 및 패키지 네이밍 표준화
- 현황 및 문제점: 공휴일·견적·계약금·배송·알림 5종의 스케줄러는 잘 구축되어 있으나 만료 시각이 지난 RefreshToken 레코드를 DB에서 정리하는 주기적 작업이 없으며, 일부 패키지명에 언더스코어(customer_order, work_order, client_notification 등)와 영문 철자 오타(production_calender)가 남아 있습니다.
- 리팩토링 방향:
  1. 매일 자정 또는 새벽 시간대에 만료된 리프레시 토큰을 일괄 삭제(refreshTokenRepository.deleteByExpiresAtBefore(LocalDateTime.now()))하는 스케줄러를 추가합니다.
  2. 자바 표준 패키지 명명 규칙에 맞춰 언더스코어를 제거하고 철자를 교정한 소문자 단일 패키지명(customerorder, workorder, productioncalendar 등)으로 리팩토링합니다.

# 1팀 리팩토링 가이드

프로젝트 종료 후 포트폴리오 완성도와 실무 운영 안정성을 높이기 위해 아래 4가지 핵심 과제를 순서대로 리팩토링하는 것을 권장합니다.

## 1. 입력 유효성 검증 메시지 세분화 및 로그인 인증 실패 한글화
- 현황 및 문제점: 전역 예외 처리기(GlobalExceptionHandler)에서 MethodArgumentNotValidException 처리 시 DTO에 정의된 필드별 검증 메시지를 추출하지 않고 고정 문자열만 반환하며, BadCredentialsException 처리 시에도 스프링 시큐리티 기본 영문 메시지('Bad credentials')를 그대로 반환하고 있습니다.
- 리팩토링 방향: BindingResult에서 필드 오류 메시지를 추출해 반환하고, 로그인 자격증명 실패 시 명확한 한글 안내 메시지를 내려주도록 개선합니다.

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErrorResponse> handleValidation(
        MethodArgumentNotValidException e
) {
    String message = e.getBindingResult().getFieldErrors().stream()
            .findFirst()
            .map(fieldError -> fieldError.getDefaultMessage())
            .orElse("요청 파라미터 값이 올바르지 않습니다.");

    return ResponseEntity.status(HttpStatus.BAD_REQUEST)
            .body(new ErrorResponse("INVALID_ARGUMENT", message));
}

@ExceptionHandler(BadCredentialsException.class)
public ResponseEntity<ErrorResponse> handleBadCredentialException(
        BadCredentialsException e
) {
    return ResponseEntity.status(HttpStatus.UNAUTHORIZED)
            .body(new ErrorResponse("UNAUTHORIZED", "이메일 또는 비밀번호가 일치하지 않습니다."));
}
```

## 2. 이메일 발송 표준 HTML 템플릿 적용
- 현황 및 문제점: 이메일 발송 클라이언트(EmailClient)가 SimpleMailMessage를 사용하여 제목과 본문 평문만 전송하고 있어, 고객이 수신했을 때 공식 서비스 안내 메일로서의 신뢰도와 가독성이 부족합니다.
- 리팩토링 방향: MimeMessage와 MimeMessageHelper를 사용하여 상단 서비스명(FixGo) 헤더, 본문 내용(줄바꿈 변환 포함), 하단 고객 포털 바로가기 버튼 및 고객센터 안내 푸터가 결합된 표준 HTML 템플릿으로 발송하도록 개선합니다.

```java
public void sendEmail(String recipientEmail, String subject, String content, String portalUrl) {
    try {
        MimeMessage mimeMessage = mailSender.createMimeMessage();
        MimeMessageHelper helper = new MimeMessageHelper(mimeMessage, true, "UTF-8");

        helper.setFrom(senderEmail);
        helper.setTo(recipientEmail);
        helper.setSubject("[FixGo] " + subject);
        helper.setText(buildHtmlTemplate(subject, content, portalUrl), true);

        mailSender.send(mimeMessage);
    } catch (MessagingException e) {
        throw new IllegalStateException("이메일 발송 중 오류가 발생했습니다.", e);
    }
}

private String buildHtmlTemplate(String title, String bodyContent, String portalUrl) {
    String formattedBody = bodyContent.replace("\n", "<br/>");
    String buttonHtml = (portalUrl != null && !portalUrl.isBlank())
            ? "<div style='margin-top:24px;'><a href='" + portalUrl + "' style='display:inline-block;padding:12px 24px;background:#2563eb;color:#ffffff;text-decoration:none;border-radius:6px;'>A/S 진행 현황 및 내역 확인하기</a></div>"
            : "";

    return "<div style='max-width:600px;margin:0 auto;font-family:sans-serif;border:1px solid #e5e7eb;border-radius:8px;overflow:hidden;'>"
            + "<div style='background:#0f172a;color:#ffffff;padding:20px 24px;font-size:20px;font-weight:bold;'>FixGo 통합 A/S 센터</div>"
            + "<div style='padding:24px;color:#1f2937;line-height:1.6;'>"
            + "<h2 style='margin-top:0;font-size:18px;color:#111827;'>" + title + "</h2>"
            + "<div>" + formattedBody + "</div>"
            + buttonHtml
            + "</div>"
            + "<div style='background:#f9fafb;padding:16px 24px;font-size:12px;color:#6b7280;border-top:1px solid #e5e7eb;'>"
            + "본 메일은 사자전자 FixGo A/S 센터에서 발송된 안내 메일입니다.<br/>문의: 고객센터 1588-0000"
            + "</div></div>";
}
```

## 3. JPA Auditing 작업자 동적 추출 및 공통 감사 상속 일원화
- 현황 및 문제점: JpaConfig의 AuditorAware가 Optional.of(1L)로 고정되어 있어 모든 생성·수정자가 1번 직원으로 기록되며, BaseEntity의 createdBy·updatedBy가 nullable = false로 설정되어 비인증 요청(외부 웹훅, 고객 포털 견적 응답) 시 제약조건 예외 위험이 있습니다. 또한 고객(Customer), 제품(Product), 제품모델(ProductModel) 엔티티는 BaseEntity를 상속하지 않고 감사 필드를 개별 선언하고 있습니다.
- 리팩토링 방향:
  1. BaseEntity의 createdBy, updatedBy 컬럼에서 nullable = false 제약을 해제하여 비인증 시스템·포털 처리 시 null 저장을 허용합니다.
  2. JpaConfig에서 SecurityContextHolder의 CustomUserDetails를 참조하여 실제 로그인한 직원 ID를 반환하도록 수정합니다.
  3. Customer, Product, ProductModel 엔티티가 모두 BaseEntity를 상속받도록 통일하고 내부 중복 감사 필드를 제거합니다.

```java
@Bean
public AuditorAware<Long> auditorProvider() {
    return () -> {
        Authentication authentication = SecurityContextHolder.getContext().getAuthentication();
        if (authentication == null || !authentication.isAuthenticated()) {
            return Optional.empty();
        }
        if (authentication.getPrincipal() instanceof CustomUserDetails userDetails) {
            return Optional.ofNullable(userDetails.getId());
        }
        return Optional.empty();
    };
}
```

## 4. AI 스트리밍 트랜잭션 분리 및 패키지·DTO 규격 정비
- 현황 및 문제점: 대문자 패키지명(AI)이 자바 표준 컨벤션에 어긋나며, OpenAIService.generateStream 메서드에 선언된 @Transactional은 Flux 반환 즉시 종료되므로 비동기 스트림 완료 콜백(doOnComplete) 시점의 DB 저장과 트랜잭션 경계가 일치하지 않습니다. 또한 채팅 이력 조회 컨트롤러가 도메인 엔티티(List<Chat>)를 외부에 직접 노출하고 있습니다.
- 리팩토링 방향:
  1. 패키지명을 소문자(net.likelion.bebc25.fixgo.ai)로 변경하고, ChatClient는 매 요청 생성 대신 생성자에서 한 번만 빌드하여 재사용합니다.
  2. generateStream 상단의 @Transactional을 제거하고, 사용자 질문 저장과 스트림 완료 후 응답 저장은 각각 분리된 트랜잭션 메서드(ChatService)를 호출하여 처리합니다.
  3. 채팅 이력 조회 API의 반환 타입을 Chat 엔티티 대신 전용 응답 Record(ChatDto.Response)로 변환합니다.
